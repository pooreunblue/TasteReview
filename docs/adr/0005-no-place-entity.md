# 0005. 가게를 별도 도메인으로 만들지 않고 리뷰의 문자열로 둔다

## 1. 맥락과 문제

맛집 리뷰 서비스에서 "가게"는 가장 중심적인 개념이다. 같은 가게의 리뷰를 모아 평균 별점을 보여주는 화면은 이 도메인에서 자연스러운 기능이다.
그러려면 가게를 독립된 개체로 만들고 리뷰가 그것을 참조해야 한다. 반대로 가게를 리뷰 안의 문자열로 두면 구현은 단순하지만 같은 가게가 여러 표기로 쌓인다.
이 선택은 데이터 모델의 뼈대이므로 나중에 바꾸면 기존 데이터 정제와 화면 재작업이 함께 필요하다.

## 2. 결정 동인

- (비목표) PRD 4절에서 가게 마스터 데이터 관리와 외부 가게 API 연동을 제외했다.
- (제약) 가게를 개체로 만들려면 동일 가게 판정 기준이 필요하다. 이름만으로는 지점 구분과 폐업·개명을 다룰 수 없고, 신뢰할 판정 기준은 외부 데이터 없이 만들 수 없다.
- (제약) 구현에 허용된 시간이 약 1시간이다(SRS 5절 C-5).
- (요구사항) 검색은 가게명 부분 일치로 동작한다(SRS-F-24). 정규화된 개체가 없어도 성립한다.
- (검증 필요) 리뷰가 실제로 쌓이는지가 먼저 확인되어야 한다(PRD 9절 성공 지표).

## 3. 검토한 대안

### 대안 A. 가게명을 리뷰의 속성(문자열)으로 둔다
리뷰가 가게명을 직접 들고 있고 가게 개체는 없다.
- 장점: 모델과 화면이 단순해 1시간 제약에 맞는다. 사용자가 입력을 자유롭게 할 수 있어 등록 마찰이 없다.
- 단점: "성수동 김밥천국"과 "김밥천국 성수점"이 별개로 쌓인다. 가게별 평균 별점이나 가게 상세 화면을 만들 수 없다.
- 다시 유력해지는 조건: 해당 없음(현 채택안).

### 대안 B. 가게 개체를 만들고 사용자가 기존 가게를 선택하거나 새로 등록한다
- 장점: 가게별 리뷰 묶음과 평균 별점이 가능해진다. 표기 편차가 억제된다.
- 단점: 중복 판정과 병합 기능이 곧 필요해지고, 잘못 등록된 가게를 정리할 관리 화면이 없으면 데이터가 빠르게 오염된다. 작성 흐름에 검색·선택 단계가 추가되어 등록 마찰이 커진다.
- 다시 유력해지는 조건: 같은 가게의 리뷰를 모아 보여주는 것이 핵심 가치로 확인될 때, 또는 표기 편차가 검색 품질 저하로 실제 관측될 때.

### 대안 C. 외부 장소 API로 가게를 식별한다
지도·장소 검색 API의 장소 식별자를 가게 키로 쓴다.
- 장점: 중복 판정 문제가 사라지고 위치·영업정보를 함께 얻는다.
- 단점: PRD가 제외한 외부 연동이며 API 키 관리와 비용, 사용 조건 검토가 필요하다. 1시간 제약과 충돌한다.
- 다시 유력해지는 조건: 지도 기반 탐색을 도입할 때. 그 시점에는 대안 B보다 이 방향이 낫다.

## 4. 결정

**우리는 가게를 별도 도메인 개체로 만들지 않고, 리뷰가 가진 문자열 속성으로 둔다.**

가장 무겁게 본 동인은 신뢰할 동일 가게 판정 기준이 없다는 점이다. 판정 기준 없이 개체를 만들면 오염된 데이터를 정리하는 관리 기능이 곧 필요해지고, 그것은 PRD가 제외한 범위다.
표기 편차는 의도적으로 감수하는 비용이며, 그 편차가 실제로 문제가 되는지를 데이터로 확인한 뒤 대안 B 또는 C로 넘어간다.

## 5. 결과

- **얻는 것**: 데이터 모델이 회원·리뷰·사진·댓글 네 개로 끝난다. 리뷰 등록 흐름에 선택 단계가 없어 작성 마찰이 낮다.
- **받아들이는 대가**: 같은 가게가 여러 표기로 쌓여 검색 결과가 흩어진다. 가게 상세 화면과 가게별 평균 별점을 제공할 수 없다. 나중에 정규화하려면 기존 데이터를 사람이 판단해 정리해야 한다.
- **후속 작업**: 표기 편차를 리스크로 명시해 추적한다(PRD 11절).
- **재검토 신호**: 출시 4주 시점에 동일 가게로 보이는 표기가 다수 관측될 때, 또는 가게별 모아보기 요구가 사용자로부터 나올 때.

## 6. 준수 확인 방법

데이터 모델에 가게를 나타내는 별도 개체가 추가되지 않았는지 검사한다(SRS 8절).
