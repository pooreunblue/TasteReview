# 0003. 저장소로 Neon PostgreSQL을 사용한다

## 1. 맥락과 문제

PRD 초안은 개발에 H2, 운영에 MySQL을 쓴다고 적었다(당시 NFR-8).
그러나 Render에 배포하기로 하면서(0002) 관리형 데이터베이스를 붙여야 하고, 개발과 운영에서 서로 다른 데이터베이스 엔진을 쓰면 SQL 방언 차이가 배포 단계에서야 드러난다. 저장소 엔진과 제공자를 정해야 한다.

## 2. 결정 동인

- (제약) 구현부터 배포까지 약 1시간(SRS 5절 C-5). 데이터베이스 프로비저닝이 몇 분 안에 끝나야 한다.
- (비용) 무료 플랜 범위에서 운영한다(SRS 5절 A-1).
- (요구사항) 영속 저장소는 하나뿐이며 로컬 파일시스템에 사용자 데이터를 두지 않는다(SRS 5절 C-4).
- (요구사항) 검색은 전체 스캔에 의존하지 않아야 한다(SRS-Q-2).
- (제약) 사진 바이너리도 같은 저장소에 담아야 한다(0004).

## 3. 검토한 대안

### 대안 A. Neon PostgreSQL(관리형, 무료 플랜)
서버리스 PostgreSQL. 접속 문자열을 발급받아 JDBC로 붙인다.
- 장점: 계정 생성부터 접속 문자열 확보까지 몇 분이면 끝난다. 무료 플랜이 있고 사용하지 않으면 컴퓨트가 정지해 비용이 들지 않는다. 표준 PostgreSQL이라 로컬에서도 동일 엔진을 쓸 수 있다.
- 단점: 유휴 후 첫 접속에 콜드 스타트 지연이 있다. 무료 플랜의 저장 용량과 동시 연결 수가 제한된다. TLS 접속만 허용해 접속 문자열에 옵션이 필요하다.
- 다시 유력해지는 조건: 해당 없음(현 채택안).

### 대안 B. Render 관리형 PostgreSQL
배포 플랫폼이 제공하는 데이터베이스를 함께 쓴다.
- 장점: 플랫폼 하나로 관리 지점이 줄고, 같은 네트워크 안이라 지연이 낮다.
- 단점: 무료 등급의 보관 기간·용량 제약이 Neon보다 불리하고, 플랫폼을 옮기면 데이터베이스도 함께 옮겨야 한다.
- 다시 유력해지는 조건: 애플리케이션과 데이터베이스 사이 네트워크 지연이 성능 문제로 측정될 때.

### 대안 C. 개발 H2 + 운영 MySQL (PRD 초안)
개발은 인메모리, 운영은 관리형 MySQL.
- 장점: 로컬에서 데이터베이스를 띄우지 않아도 개발이 시작된다.
- 단점: 두 엔진의 방언 차이로 로컬에서 통과한 쿼리가 배포 후 실패할 수 있다. 1시간 제약에서 그 디버깅 비용은 치명적이다. 인메모리는 재기동마다 데이터가 사라져 실제 동작 확인이 번거롭다.
- 다시 유력해지는 조건: 네트워크 없이 개발해야 하는 상황이 생길 때. 그때도 운영 엔진과 동일한 PostgreSQL을 로컬 컨테이너로 띄우는 편이 낫다.

## 4. 결정

**우리는 개발과 운영 모두에서 Neon이 제공하는 PostgreSQL을 단일 저장소로 사용한다.**

가장 무겁게 본 동인은 환경 간 엔진 차이를 없애는 것이다. 1시간 안에 끝내야 하는 작업에서 방언 차이로 인한 배포 후 디버깅은 허용할 수 없는 비용이다.
제공자를 Neon으로 택한 이유는 프로비저닝이 가장 빠르고 무료 플랜에서 유휴 시 비용이 발생하지 않기 때문이다.

## 5. 결과

- **얻는 것**: 로컬에서 검증한 쿼리가 배포 환경에서 동일하게 동작한다. 데이터베이스 운영 작업이 없다.
- **받아들이는 대가**: 개발 중에도 네트워크와 접속 정보가 필요하다. 유휴 후 첫 요청에 콜드 스타트가 겹친다(0002의 인스턴스 콜드 스타트와 합산된다). 무료 플랜의 용량·연결 수 상한을 관리해야 한다.
- **후속 작업**: 접속 정보를 환경변수로만 주입하고(0006), 접속 문자열에 TLS 옵션을 포함한다. 커넥션 풀 최대 크기를 작게 두고 설정으로 조정 가능하게 한다(SRS 7.2).
- **재검토 신호**: 무료 플랜 용량 한도에 근접할 때, 동시 연결 부족이 관측될 때, 애플리케이션-데이터베이스 지연이 성능 기준을 위협할 때.

## 6. 준수 확인 방법

애플리케이션 설정에 데이터베이스 접속 정보 리터럴이 없고 환경변수 참조만 있는지 검사한다.
로컬과 배포 환경 모두에서 동일 스키마로 기동되는지 확인한다(SRS-F-38).
