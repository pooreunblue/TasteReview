# 0002. Render에 컨테이너 이미지로 배포한다

## 1. 맥락과 문제

서비스를 외부에서 접근 가능한 주소로 띄워야 하는데, 서버를 직접 운영할 인력과 시간이 없다.
배포 대상과 실행 방식(직접 실행 가능한 JAR인지 컨테이너 이미지인지)을 정해야 하며, 이 선택은 설정 주입 방식·파일 저장 가능 여부·헬스 체크 방식까지 함께 결정한다.

## 2. 결정 동인

- (제약) 구현부터 배포까지 약 1시간 안에 끝나야 한다(SRS 5절 C-5).
- (제약) 운영 인력이 없어 OS 패치와 프로세스 관리를 직접 하지 않아야 한다.
- (비용) 초기에는 무료 플랜 범위에서 운영한다(SRS 5절 A-1).
- (요구사항) 동일한 산출물이 로컬과 배포 환경에서 환경변수만 바꿔 동작해야 한다(SRS-Q-9).
- (요구사항) 기동 후 60초 이내에 헬스 체크가 정상 응답해야 한다(SRS-Q-8).

## 3. 검토한 대안

### 대안 A. Render + 컨테이너 이미지(Dockerfile)
저장소를 연결하고 Dockerfile로 빌드된 이미지를 Render가 실행한다.
- 장점: 런타임·JDK 버전·실행 사용자를 이미지에 고정해 로컬과 배포의 차이를 없앨 수 있다. `PORT`와 환경변수 주입, 헬스 체크, 자동 재배포가 플랫폼 기능으로 제공된다. 무료 플랜이 있다.
- 단점: 무료 인스턴스는 유휴 시 중지되어 첫 요청에 콜드 스타트가 발생한다. 파일시스템이 휘발성이라 업로드 파일을 저장할 수 없다. 메모리 상한이 낮다.
- 다시 유력해지는 조건: 해당 없음(현 채택안).

### 대안 B. Render의 네이티브 Java 빌드(Dockerfile 없이)
플랫폼이 Gradle 빌드를 감지해 실행한다.
- 장점: Dockerfile을 작성하지 않아 초기 작업이 한 단계 줄어든다.
- 단점: JDK 버전과 실행 옵션이 플랫폼 감지에 의존해 로컬과 동일함을 보장하기 어렵다. 이미지가 곧 산출물이 아니어서 다른 플랫폼으로 옮길 때 재작업이 생긴다.
- 다시 유력해지는 조건: 컨테이너 이미지 유지 부담이 실제로 문제가 되고 플랫폼을 옮길 계획이 없을 때.

### 대안 C. 클라우드 VM(EC2 등) 직접 운영
VM을 띄워 JAR을 실행하고 리버스 프록시를 둔다.
- 장점: 파일시스템이 영구적이어서 업로드 파일을 로컬에 둘 수 있고, 자원 제약이 자유롭다.
- 단점: OS 패치, 프로세스 관리, TLS 인증서, 배포 스크립트를 모두 직접 만들어야 해 1시간 제약과 정면으로 충돌한다.
- 다시 유력해지는 조건: 무료 플랜 제약(콜드 스타트, 메모리, 휘발성 디스크)이 서비스 품질을 실제로 해칠 때.

## 4. 결정

**우리는 Render에 다단계 Dockerfile로 빌드한 컨테이너 이미지를 배포한다.**

가장 무겁게 본 동인은 운영 부담 없이 1시간 안에 배포까지 끝내는 것이다.
Dockerfile을 쓰는 쪽을 택한 이유는 런타임을 산출물에 고정해야 로컬과 배포의 동작 차이를 없앨 수 있고(SRS-Q-9), 나중에 플랫폼을 옮길 때 이미지를 그대로 가져갈 수 있기 때문이다.

## 5. 결과

- **얻는 것**: 서버 운영 작업이 사라진다. 환경변수 주입과 헬스 체크를 플랫폼이 담당한다. 이미지가 이식 가능한 산출물로 남는다.
- **받아들이는 대가**: 무료 인스턴스의 콜드 스타트를 사용자가 체감한다. 이 때문에 성능 요구(SRS-Q-1)의 측정 조건에서 콜드 스타트 요청을 제외해야 했다. 파일시스템에 사용자 데이터를 둘 수 없어 사진 저장 방식이 제약된다(0004 참고).
- **후속 작업**: 실행 단계를 JRE로 제한하고 비루트 사용자로 실행하는 Dockerfile 작성(SRS-Q-11, SRS-Q-12), 헬스 체크 경로 노출(SRS-F-37).
- **재검토 신호**: 콜드 스타트나 메모리 상한이 실사용 불만으로 보고될 때, 또는 인스턴스를 2대 이상 운영해야 할 때.

## 6. 준수 확인 방법

Dockerfile에 빌드 단계와 실행 단계가 분리되어 있고 실행 단계에 빌드 도구가 없는지 검사한다.
동일 이미지를 로컬에서 환경변수만 바꿔 기동해 본다(SRS-Q-9).
