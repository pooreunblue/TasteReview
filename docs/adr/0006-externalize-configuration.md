# 0006. 변경 가능한 모든 설정값을 환경변수로 외부화한다

## 1. 맥락과 문제

접속 정보뿐 아니라 페이지 크기, 사진 장수 제한, 별점 범위, 검색 최소 키워드 길이, 선택 가능한 지역 목록 같은 값들이 여러 계층에 흩어져 등장한다.
이런 값을 코드나 템플릿에 직접 적으면 값을 하나 바꿀 때마다 다시 빌드하고 배포해야 하며, 같은 값이 여러 곳에 중복되어 서로 어긋난다.
또한 아직 확정되지 않은 값(지역 분류 체계 등)을 코드에 고정하면 결정이 바뀔 때 수정 범위가 넓어진다. 설정을 어디에 두고 어떻게 주입할지 정해야 한다.

## 2. 결정 동인

- (지시) 가능한 한 하드코딩을 피하고 환경변수·설정으로 작성한다(SRS 5절 C-6).
- (요구사항) 동일한 이미지가 로컬과 Render에서 환경변수만 바꿔 동작해야 한다(SRS-Q-9).
- (제약) 비밀값(데이터베이스 비밀번호)은 저장소에 남으면 안 된다.
- (미확정) 지역 목록, 별점 단위 등 아직 합의되지 않은 값이 여러 개 있다(SRS 5절 A-3, A-4).
- (제약) 구현 시간이 약 1시간이므로 설정 체계 자체가 복잡해서는 안 된다.

## 3. 검토한 대안

### 대안 A. 설정 파일에서 환경변수를 참조하고, 값은 배포 환경이 주입한다
`${환경변수:기본값}` 형태로 참조하고 기본값을 설정 파일에 둔다. 코드는 바인딩된 설정 객체만 읽는다.
- 장점: 배포 환경에서 재빌드 없이 값을 바꿀 수 있다. 기본값이 설정 파일에 모여 있어 어떤 값이 조정 가능한지 한눈에 보인다. 비밀값은 환경변수로만 들어와 저장소에 남지 않는다. 컨테이너 배포 방식과 그대로 맞는다.
- 단점: 환경변수 이름이 늘어나 문서화가 필요하다. 오타로 인한 기본값 적용을 알아채기 어려울 수 있다.
- 다시 유력해지는 조건: 해당 없음(현 채택안).

### 대안 B. 프로파일별 설정 파일에 값을 적어 둔다
`application-prod.yaml` 등에 환경별 값을 직접 적는다.
- 장점: 값이 파일에 명시되어 이력 추적이 쉽다.
- 단점: 비밀값이 저장소에 들어간다. 값 하나를 바꾸려면 커밋과 재배포가 필요하다. 배포 환경이 늘면 파일도 늘어난다.
- 다시 유력해지는 조건: 비밀값이 전혀 없고 환경이 하나로 고정될 때.

### 대안 C. 코드에 상수로 두고 필요할 때 수정한다
- 장점: 초기 작성이 가장 빠르다.
- 단점: 같은 값이 컨트롤러·서비스·템플릿에 중복되어 어긋난다. 값 변경마다 재배포가 필요하고, 미확정 값이 코드 여러 곳에 퍼진다.
- 다시 유력해지는 조건: 없음. 이번 지시(C-6)와 정면으로 충돌한다.

## 4. 결정

**우리는 변경 가능한 모든 설정값을 환경변수로 주입받고, 설정 파일에는 기본값만 두며, 코드에는 이 값들의 리터럴을 두지 않는다.**

가장 무겁게 본 동인은 미확정 값이 많다는 점이다. 지역 목록처럼 아직 합의되지 않은 값을 설정 경계 밖으로 빼 두면, 결정이 바뀌어도 코드를 고치지 않고 환경변수만 바꿔 대응할 수 있다.
비밀값을 저장소에서 분리하는 것도 같은 방식으로 함께 해결된다.

## 5. 결과

- **얻는 것**: 값 변경이 재배포 없이 가능하다. 미확정 사항이 구현을 막지 않는다. 비밀값이 저장소에 남지 않는다. 동일 이미지가 환경을 넘나든다(SRS-Q-9).
- **받아들이는 대가**: 환경변수 목록을 문서로 유지해야 한다(SRS 7.3). 변수명 오타가 조용히 기본값 적용으로 이어질 수 있다. 설정 객체 바인딩 코드가 추가된다.
- **후속 작업**: 필수 환경변수 누락 시 기동을 중단하고 누락 변수명을 로그에 남긴다(SRS-F-35). 설정 항목 표를 SRS 7.3에 유지한다.
- **재검토 신호**: 환경변수 개수가 관리 한계를 넘어 설정 서버나 비밀 관리 도구가 필요해질 때.

## 6. 준수 확인 방법

코드와 템플릿에서 페이지 크기·파일 크기·별점 범위·지역 목록·접속 정보 리터럴을 검색해 발견되지 않는지 검사한다(SRS-F-34).
필수 환경변수를 비운 채 기동해 프로세스가 중단되는지 확인한다(SRS-F-35).
