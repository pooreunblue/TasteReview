# 0001. 맛집 리뷰 서비스 MVP

## 1. 한 줄 요약

맛집을 다녀온 사람이 사진과 별점이 담긴 리뷰를 남기고, 다른 사람이 그 리뷰를 검색해 찾아보고 댓글로 물어볼 수 있는 서버 렌더링 웹 서비스.

## 2. 배경과 문제

맛집 정보를 찾는 사람은 지금 포털 리뷰, SNS 게시물, 지인 대화에 흩어진 정보를 직접 긁어모아야 한다.
포털 리뷰는 광고성 글이 섞여 신뢰하기 어렵고, SNS는 검색이 사실상 해시태그에 의존해 "성수동에서 4점 이상" 같은 조건으로 좁힐 수 없다.
반대로 리뷰를 쓰는 쪽도 남길 곳이 마땅치 않다. 짧은 감상을 올릴 공간은 많지만, 어느 가게의 몇 점짜리 경험인지가 구조화되어 남지 않아 나중에 자신조차 다시 찾지 못한다.
그 결과 실제 방문 경험이 축적되지 않고 매번 처음부터 검색하는 일이 반복된다.

이 서비스는 "다녀온 가게에 대한 구조화된 경험"을 모으고, 그것을 조건으로 찾아볼 수 있게 만드는 것을 출발점으로 삼는다.

## 3. 목표

- 방문자가 가게명·지역·별점·사진이 포함된 리뷰를 5분 안에 등록할 수 있게 한다.
- 키워드와 지역·별점 조건으로 원하는 리뷰를 찾을 수 있게 한다.
- 리뷰를 읽은 사람이 댓글로 추가 정보를 묻고 답할 수 있게 한다.
- 위 세 흐름이 JavaScript 없이 서버 렌더링만으로 완결되도록 해, 초기 구현과 운영 부담을 낮춘다.

## 4. 비목표

이번 범위에서 제외하는 것과 이유는 다음과 같다. 범위를 넓히는 판단보다 이 목록을 지키는 편이 1단계 출시 시점을 결정한다.

- **가게 마스터 데이터 관리와 외부 가게 API 연동** — 가게를 식별자로 정규화하려면 별도 데이터 확보가 필요하다. MVP에서는 가게명을 리뷰에 직접 입력받는 문자열로 둔다.
- **지도 기반 탐색** — 좌표 수집과 지도 API 비용·키 관리가 따라붙는다. 지역은 텍스트 분류로만 다룬다.
- **대댓글, 좋아요·추천, 팔로우** — 댓글이 실제로 쓰이는지 확인하기 전에는 상호작용을 늘릴 근거가 없다.
- **신고·차단·관리자 화면** — 이용자 규모가 작은 초기에는 운영자가 DB에서 직접 처리하는 편이 빠르다.
- **소셜 로그인, 비밀번호 찾기, 이메일 인증** — 자체 로그인만으로 작성자 식별이라는 목적은 충족된다.
- **REST API 공개와 SPA 전환** — 화면은 서버 렌더링으로 고정한다. API가 필요해지는 시점은 별도 PRD로 다룬다.
- **알림(메일·푸시)** — 댓글이 달렸는지는 사용자가 직접 확인한다.

## 5. 사용자와 시나리오

- **리뷰 작성자**: 외식을 자주 하고 기록을 남기고 싶은 사람. 방문 직후 모바일에서 사진 몇 장과 함께 짧게 남기고 싶다.
- **리뷰 탐색자**: 특정 지역에서 갈 만한 곳을 찾는 사람. 로그인 없이 먼저 둘러보고, 궁금한 점이 생기면 그때 가입한다.

주요 시나리오:

1. 탐색자가 홈에 들어와 "성수동"을 검색하고, 별점 4점 이상 필터를 걸어 목록을 훑은 뒤 마음에 드는 리뷰를 연다.
2. 탐색자가 상세 페이지에서 "주차 가능한가요?"라고 댓글을 남기려다 로그인 페이지로 이동하고, 가입 후 원래 보던 리뷰로 돌아와 댓글을 단다.
3. 작성자가 식사 직후 휴대폰으로 사진 3장을 올리고 별점과 한 문단 감상을 적어 리뷰를 등록한다.
4. 작성자가 오타를 발견하고 자신의 리뷰를 수정한다. 남의 리뷰 수정 주소로 직접 접근하면 거부된다.

## 7. 화면과 흐름

서버 렌더링(Thymeleaf) 기준이므로 화면 전환은 모두 페이지 이동이며, 상태 변경은 POST 후 리다이렉트로 처리한다.

| 화면 | 경로 | 설명 |
| --- | --- | --- |
| 리뷰 목록 / 검색 결과 | `GET /reviews` | 홈이자 검색 결과 화면. 조건은 `keyword`, `region`, `minRating`, `sort`, `page` 파라미터로 받는다 |
| 리뷰 상세 | `GET /reviews/{id}` | 리뷰 본문·사진·댓글 목록. 댓글 페이지는 `page` 파라미터 |
| 리뷰 작성 | `GET /reviews/new` → `POST /reviews` | 로그인 필요. 성공 시 생성된 상세로 리다이렉트 |
| 리뷰 수정 | `GET /reviews/{id}/edit` → `POST /reviews/{id}` | 작성자만 접근 |
| 리뷰 삭제 | `POST /reviews/{id}/delete` | 확인 단계를 거친 뒤 목록으로 리다이렉트 |
| 댓글 등록 | `POST /reviews/{id}/comments` | 성공 시 해당 상세로 리다이렉트 |
| 댓글 삭제 | `POST /reviews/{id}/comments/{commentId}/delete` | 댓글 작성자만 |
| 회원가입 | `GET /signup` → `POST /signup` | 성공 시 로그인 화면으로 |
| 로그인 / 로그아웃 | `GET /login` → `POST /login`, `POST /logout` | 로그인 후 직전에 시도한 화면으로 복귀 |

## 8. 도메인과 데이터

다루는 개념은 네 가지다. 구체적인 테이블 설계와 매핑은 구현 단계에서 정한다.

- **회원(Member)**: 이메일, 비밀번호 해시, 닉네임, 가입 시각. 이메일과 닉네임은 각각 유일하다.
- **리뷰(Review)**: 작성 회원, 가게명, 지역, 별점, 제목, 본문, 작성·수정 시각. 회원 1명이 리뷰 여러 개를 가진다.
- **리뷰 사진(ReviewImage)**: 소속 리뷰, 저장 식별자, 원본 파일명, 노출 순서. 리뷰 1건에 최대 5장이 속한다.
- **댓글(Comment)**: 소속 리뷰, 작성 회원, 내용, 작성 시각. 리뷰 1건에 댓글 여러 개가 속한다.

가게는 별도 개념으로 만들지 않고 리뷰가 가진 문자열로 둔다(4절 참고). 같은 가게의 리뷰를 묶는 기능은 이번 범위가 아니다.
지역은 자유 입력이 아니라 선택 목록으로 받아야 필터가 성립한다. 분류 체계는 12절 미해결 질문으로 남긴다.
목록에 댓글 수를 노출하므로(FR-13) 조회할 때마다 댓글을 세는 구조는 NFR-1과 충돌할 수 있다. 집계 방식은 구현 시 검토한다.

## 9. 성공 지표

출시 후 4주 시점에 아래를 본다. 수치는 초안이며 확정 전 합의가 필요하다(12절).

| 지표 | 목표 | 측정 방법 |
| --- | --- | --- |
| 등록된 리뷰 수 | 200건 | 리뷰 테이블 집계 |
| 작성 폼 진입 대비 등록 완료율 | 60% | `GET /reviews/new` 대비 등록 성공 건수 |
| 검색을 한 번 이상 사용한 세션 비율 | 40% | 접근 로그에서 `keyword`·`region` 파라미터 포함 요청 비율 |
| 리뷰당 평균 댓글 수 | 0.5건 | 댓글 수 / 리뷰 수 |
| 재방문 작성자 비율 | 리뷰 2건 이상 작성자 25% | 회원별 리뷰 수 집계 |

검색 사용률이 목표에 크게 못 미치면 탐색 방식(목록 큐레이션, 지역 첫 화면 노출)을 다시 검토하고, 댓글 수가 바닥이면 상호작용 기능을 늘리기 전에 댓글을 유지할지부터 판단한다.

## 11. 리스크와 대응

| 리스크 | 영향 | 대응 |
| --- | --- | --- |

| 부적절한 사진이 올라온다 | 서비스 노출 위험 | 초기에는 운영자 수동 삭제로 대응하고, 삭제 경로와 담당자를 출시 전에 정해 둔다 |
| 가게명을 자유 입력으로 두어 같은 가게가 여러 표기로 쌓인다 | 검색 품질이 떨어진다 | 의도된 절충임을 명시하고, 표기 편차가 실제로 문제가 되는지 4주 뒤 데이터로 확인한다 |
