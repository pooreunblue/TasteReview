# 디자인 관리 스킬

TasteReview에서 Claude는 코드를 직접 구현하지 않고 설계와 리뷰만 담당한다(루트 `CLAUDE.md` 참고).
디자인 작업에서도 마찬가지로, CSS를 대신 써 주는 대신 어떤 토큰을 어디에 쓸지 정하고 규칙 위반을 찾아내는 역할을 한다.

## 단일 출처는 DESIGN.md

색·폰트·여백·컴포넌트 규칙은 루트 `DESIGN.md`에만 정의한다. 화면 작업을 시작하기 전에 이 문서를 읽고, 여기 있는 토큰으로 구성할 수 있는지부터 확인한다.
값이 여러 곳에 흩어지면 화면마다 조금씩 다른 색과 간격이 생기고, 그 차이는 나중에 전수 조사 없이는 되돌릴 수 없다.

`DESIGN.md`가 확정한 네 가지 원칙은 협상 대상이 아니다.

1. 모바일 우선. 기준 폭 360px, 어떤 폭에서도 가로 스크롤 없음.
2. 따뜻한 색감. 중립 회색 대신 붉은기·노란기가 섞인 색.
3. Pretendard 단일 서체. 위계는 크기와 굵기로만 만든다.
4. 여백은 8의 배수. 1px 테두리와 2px 포커스 링만 예외.

## 화면을 설계할 때

1. **`DESIGN.md`를 읽는다.** 토큰 표와 컴포넌트 규칙을 확인한다.
2. **모바일 레이아웃을 먼저 정한다.** 360px 한 열에서 무엇이 보이고 무엇이 접히는지 결정한 다음 넓은 화면을 다룬다. 반대 순서로 하면 데스크톱에서 자연스러운 구성이 모바일에서 무너진다.
3. **기존 컴포넌트로 조립한다.** 새 컴포넌트를 만들기 전에 버튼·카드·입력·배지·배너·빈 상태의 조합으로 표현되는지 본다.
4. **터치와 입력을 확인한다.** 터치 대상 44×44px, 입력 글자 16px 이상. 이 둘은 모바일에서 가장 자주 깨지고, 깨지면 화면 확대나 오터치로 바로 드러난다.
5. **토큰으로 표현되지 않는 값이 필요하면 먼저 문서를 고친다.** 화면에 임의 값을 넣고 나중에 정리하는 순서는 실제로 정리되지 않는다.

## DESIGN.md를 갱신할 때

- 색을 추가하면 배경 대비를 계산해 표에 함께 적는다. 본문 텍스트 4.5:1, 아이콘·테두리 3:1이 하한이다. 수치 없이 추가된 색은 나중에 누구도 검증하지 않는다.
- 다크 모드 값을 함께 정의한다. 라이트 값만 추가하면 다크 모드에서 대비가 무너진 채로 배포된다.
- 여백 토큰은 8의 배수만 추가한다. 7px이나 12px이 필요해 보이면 대개 레이아웃 구조가 잘못된 것이다.
- 변경하면 문서 맨 아래 변경 이력에 날짜와 내용을 남긴다.
- 원칙 자체를 바꾸는 변경(예: 서체 교체, 색 기조 변경)은 되돌리기 비용이 크므로 `adr` 스킬로 ADR을 함께 남긴다.

## 디자인을 리뷰할 때

`references/review-checklist.md`를 읽고 그 항목을 기준으로 지적한다.
어느 파일의 어떤 값이 어떤 규칙을 어겼고 무엇으로 바꿔야 하는지를 짝지어 제시한다. "간격이 어색하다" 같은 지적은 고칠 대상을 특정하지 못한다.
규칙 위반이 아니라 취향 차이인 부분은 그렇다고 밝히고 사용자 판단에 맡긴다.
