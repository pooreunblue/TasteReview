# PRD 작성 스킬

TasteReview에서 Claude는 코드를 직접 구현하지 않고 설계와 리뷰만 담당한다(루트 `CLAUDE.md` 참고).
그래서 PRD는 "무엇을 왜 만드는가"를 사용자와 합의해 남기는 가장 중요한 산출물이다.
구현 코드를 쓰는 대신, 구현자가 읽고 바로 만들 수 있을 만큼 구체적인 문서를 만드는 것이 목표다.

## 관리 규칙

모든 PRD는 `docs/prd/` 아래에 한 기능당 한 파일로 둔다.

- 파일명: `docs/prd/NNNN-slug.md` (예: `docs/prd/0001-review-write.md`)
- `NNNN`은 4자리 zero-pad 일련번호, `slug`는 영문 소문자 kebab-case
- `docs/prd/README.md`는 인덱스 표이며, PRD를 추가하거나 상태를 바꿀 때마다 같이 갱신한다
- 상태값은 `Draft` → `Review` → `Approved` → `In Progress` → `Done`, 폐기 시 `Dropped`
- 템플릿은 `assets/prd-template.md`에 있다. 새 PRD는 이 템플릿을 복사해서 시작한다

## 작업 순서

1. **기존 문서 확인.** `docs/prd/README.md`와 파일 목록을 읽어 다음 번호를 정하고, 같은 주제의 PRD가 이미 있으면 새로 만들지 말고 그 문서를 갱신한다.
2. **모르는 것을 먼저 묻는다.** 사용자가 이미 말한 내용은 다시 묻지 않는다. 대신 답에 따라 문서가 크게 달라지는 것만 골라 한 번에 3~4개까지 묻는다. 대표적으로 대상 사용자, 이번 범위에서 뺄 것, 성공 판단 기준, 기존 도메인과의 관계다.
3. **초안 작성.** 템플릿의 모든 절을 채우되, 확정되지 않은 내용은 비워 두지 말고 "미해결 질문"에 질문 형태로 옮긴다. 추측을 사실처럼 쓰면 구현자가 잘못된 전제로 만들게 된다.
4. **인덱스 갱신.** `docs/prd/README.md` 표에 행을 추가하거나 상태를 고친다.
5. **요약 보고.** 파일 경로, 핵심 결정 사항, 사용자 확인이 필요한 미해결 질문을 짧게 전달한다.

## 작성 품질 기준

- **요구사항은 검증 가능하게.** "빠르게 보여준다"가 아니라 "목록 20건을 1초 안에 렌더링한다"처럼 참/거짓을 판정할 수 있게 쓴다. 판정할 수 없는 문장은 리뷰에서도 통과 여부를 가릴 수 없다.
- **요구사항마다 ID를 붙인다.** `FR-1`, `NFR-1` 형태로 두면 이후 리뷰와 구현 논의에서 문장을 그대로 인용하지 않고 번호로 가리킬 수 있다.
- **비목표를 반드시 적는다.** 범위를 넓히는 것보다 좁히는 문장이 구현 분량을 실제로 통제한다.
- **해결책이 아니라 문제부터.** 배경 절에서 화면이나 테이블 설계를 먼저 못 박으면 더 나은 대안을 검토할 기회가 사라진다.
- **기술 스택은 제약으로만 언급한다.** 이 프로젝트는 Java 17, Spring Boot 4.1.1, Thymeleaf(서버 렌더링), Gradle, Lombok을 쓴다. 구현 코드를 PRD에 넣지 말고, 화면 전환이 서버 렌더링 기준이라는 식의 제약만 적는다.
- **분량은 기능 크기에 맞춘다.** 작은 기능에 억지로 모든 절을 늘려 쓰면 정작 중요한 결정이 묻힌다. 해당 없는 절은 "해당 없음"과 그 이유를 한 줄로 남긴다.

## 기존 PRD를 고칠 때

내용을 바꾸면 문서 맨 아래 "변경 이력"에 날짜·변경 요약을 한 줄 추가하고, 프런트매터의 `최종 수정일`과 상태를 함께 갱신한다.
이미 `Approved` 이상인 문서의 요구사항을 바꿀 때는 조용히 덮어쓰지 말고, 무엇이 왜 바뀌는지 사용자에게 먼저 알린다.

## PRD를 리뷰할 때

리뷰 요청을 받으면 `references/review-checklist.md`를 읽고 그 항목을 기준으로 지적한다.
문서를 다시 써 주기보다, 어느 절의 어떤 문장이 왜 문제인지와 대안을 제시하는 편이 사용자가 판단하기 쉽다.
