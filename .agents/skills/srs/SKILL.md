# SRS 작성 스킬

TasteReview에서 Claude는 코드를 직접 구현하지 않고 설계와 리뷰만 담당한다(루트 `CLAUDE.md` 참고).
SRS는 그 원칙에서 가장 구현에 가까운 산출물이다. 구현자가 이 문서만 읽고도 무엇을 만들어야 하는지, 무엇을 만들면 완료인지 판단할 수 있어야 한다.

## PRD와의 경계

둘을 섞으면 문서가 길어지기만 하고 어느 쪽 질문에도 답하지 못한다. 경계는 이렇게 잡는다.

- **PRD**는 왜 만드는지와 누구에게 어떤 가치를 주는지를 다룬다. 비목표, 성공 지표, 우선순위가 여기에 있다.
- **SRS**는 시스템이 어떻게 행동해야 하는지를 다룬다. 사전조건, 처리 규칙, 사후조건, 예외 흐름, 인터페이스 계약, 검증 방법이 여기에 있다.
- SRS는 설계서가 아니다. 클래스 구조, 알고리즘 선택, 라이브러리 결정은 넣지 않는다. 다만 화면 경로와 폼 필드처럼 외부에서 관찰되는 계약은 SRS의 몫이다.

PRD 없이 SRS를 요청받으면, 목적과 범위가 합의되지 않은 채 상세 명세를 쓰는 셈이라 되돌리는 비용이 크다. 먼저 `prd` 스킬로 PRD를 만들자고 제안하고, 사용자가 그대로 진행하길 원하면 SRS 1절에 "선행 PRD 없음"과 그 사유를 남긴다.

## 관리 규칙

모든 SRS는 `docs/srs/` 아래에 한 파일로 둔다.

- 파일명: `docs/srs/NNNN-slug.md` (예: `docs/srs/0001-taste-review-mvp.md`)
- `NNNN`은 4자리 zero-pad 일련번호이며 PRD 번호와는 별개로 매긴다. 대응 관계는 프런트매터 `출처 PRD` 필드로 남긴다
- `docs/srs/README.md`는 인덱스 표이며, 문서를 추가하거나 상태를 바꿀 때마다 같이 갱신한다
- 상태값은 `Draft` → `Review` → `Baselined` → `Superseded`. `Baselined`는 구현 착수 기준선이라는 뜻이다
- 템플릿은 `assets/srs-template.md`에 있다

## 작업 순서

1. **선행 PRD를 읽는다.** `docs/prd/`에서 대상 PRD를 찾아 목표·비목표·요구사항 ID를 확보한다. PRD의 비목표는 SRS에서도 범위 밖이며, 몰래 되살아나지 않는지 끝까지 확인한다.
2. **기존 SRS를 확인한다.** `docs/srs/README.md`로 다음 번호를 정하고, 같은 대상의 SRS가 있으면 새로 만들지 말고 갱신한다.
3. **PRD의 공백을 식별한다.** PRD의 기능 요구사항 하나하나에 대해 사전조건, 예외, 동시성, 권한, 데이터 제약을 자문한다. PRD가 답하지 않는 것이 SRS에서 결정해야 할 목록이다.
4. **결정이 필요한 것만 묻는다.** 3번에서 나온 공백 중 답에 따라 명세가 크게 갈리는 것만 한 번에 3~4개까지 묻는다. 나머지는 합리적인 기본값으로 쓰되 "가정"으로 표시한다.
5. **명세 작성.** 템플릿을 따르고, 요구사항마다 ID와 검증 방법을 붙인다.
6. **추적 매트릭스 작성.** PRD 요구사항 ID와 SRS 요구사항 ID를 연결한다. 어느 쪽에도 짝이 없는 행이 있으면 누락이거나 범위 이탈이므로 반드시 사용자에게 알린다.
7. **인덱스 갱신과 요약 보고.** 파일 경로, 핵심 결정, 확인이 필요한 미해결 이슈를 짧게 전달한다.

## 작성 품질 기준

- **하나의 요구사항에는 하나의 검증 가능한 진술만.** "그리고", "또한"으로 이어진 문장은 나누는 편이 좋다. 절반만 충족된 요구사항은 통과 여부를 판정할 수 없다.
- **정상 흐름보다 예외 흐름이 중요하다.** 입력 검증 실패, 권한 없음, 대상 없음, 중복 요청, 동시 수정, 외부 자원 실패를 각 기능마다 따진다. 구현자가 가장 자주 되묻는 지점이 여기다.
- **요구사항마다 검증 방법을 적는다.** 시험(T), 검사(I), 시연(D), 분석(A) 중 무엇으로 확인할지 표시하면, 나중에 테스트 계획이 이 문서에서 그대로 나온다.
- **수치 없는 품질 요구사항은 쓰지 않는다.** "안정적이어야 한다"는 검증할 수 없다. 조건·부하·측정 지점을 함께 적는다.
- **확정되지 않은 것은 가정으로 명시한다.** 추측을 단정형으로 쓰면 구현자가 잘못된 전제로 만든다. 가정은 5절에, 답이 필요한 것은 12절 미해결 이슈에 둔다.
- **기술 스택은 제약으로만 다룬다.** 이 프로젝트는 Java 17, Spring Boot 4.1.1, Thymeleaf(서버 렌더링), Gradle, Lombok을 쓴다. 코드나 엔티티 정의를 넣지 말고, 상태 변경은 POST 후 리다이렉트로 관찰된다는 식의 외부 동작 제약으로 적는다.

## 기존 SRS를 고칠 때

내용을 바꾸면 변경 이력에 날짜·변경 요약·영향받는 요구사항 ID를 남기고, 프런트매터의 `최종 수정일`과 상태를 갱신한다.
`Baselined` 이후의 변경은 구현에 직접 영향을 주므로 조용히 덮어쓰지 말고, 무엇이 왜 바뀌며 어떤 요구사항이 영향을 받는지 먼저 알린다.
대상 PRD가 바뀌었다면 추적 매트릭스부터 다시 맞춘다. 짝 없는 요구사항이 생기는 지점이 곧 놓친 변경이다.

## SRS를 리뷰할 때

리뷰 요청을 받으면 `references/review-checklist.md`를 읽고 그 항목을 기준으로 지적한다.
문서를 대신 다시 써 주기보다, 어느 요구사항이 왜 검증 불가능하거나 모호한지와 대안 문장을 함께 제시하는 편이 사용자가 판단하기 쉽다.
