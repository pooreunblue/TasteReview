# TDD·BDD 테스트 스킬

TasteReview는 직접 코드를 작성하지 않지만, 기능 개발은 "테스트가 곧 명세"인 TDD·BDD로 체계화한다.
산출물은 코드가 아니라 아래 네 가지 지침이고, 구현자는 이 지침만으로 RED→GREEN→REFACTOR를 밟는다.

## 원칙

- **테스트를 먼저 쓴다.** 기능을 구현하기 전에 그 기능이 무엇을 하는지 테스트로 고정한다. 테스트가 없으면 명세가 없다.
- **행위는 given/when/then으로 명세한다.** given은 전제, when은 동작, then은 검증. 하나의 테스트는 하나의 시나리오이고, 시나리오는 하나의 결과만 검증한다.
- **주기는 RED → GREEN → REFACTOR다.** 실패하는 테스트(코드 없이도 컴파일 실패거나 어서션 실패)를 먼저 보여 준 뒤, 그걸 통과시키는 최소 구현을 지시하고, 중복·이름을 정리하는 단계를 마지막에 둔다.
- **우리가 쓰는 스택 문법은 spring-boot4 스킬을 따른다.** 표현(어노테이션·스타터·좌표)이 헷갈리면 그 스킬의 `references/latest-syntax.md`를 읽는다.

## 작업 순서

1. **행위 명세.** 요청받은 기능의 시나리오를 given/when/then으로 2~5개 풀어 사용자와 합의한다. 예외·경계·권한 없는 경우가 빠지면 되묻는다.
2. **테스트 레벨 결정.** 단위(서비스·로직), 슬라이스(컨트롤러·리포지토리), 통합(@SpringBootTest) 중 무엇으로 검증할지 정하고 근거를 한 줄 제시한다.
3. **테스트 작성 지침(RED).** 파일 경로·클래스명·어노테이션·목 협력 라이브러리·픽스처를 지침으로 준다. 이때 실제 테스트 코드는 작성하지 말고, 무엇을 어떻게 적을지와 컴파일/실행을 확인하라는 지침만 준다.
4. **실패 확인에 대한 지침(RED 확인).** `./gradlew test`로 실패가 떠야 한다는 것과 실패 원인을 해석하는 법을 알려 준다.
5. **최소 구현 지침(GREEN).** 테스트를 통과시키는 가장 짧은 구현 방향을 제시한다. 클래스·메서드 시그니처 수준까지만 적고 상세 코드는 적지 않는다(작성은 사용자의 몫).
6. **리팩터링 지침(REFACTOR).** 중복 제거·이름 정리 앞에 테스트가 안전망이라는 사실을 짚는다.
7. **최종 확인.** `./gradlew test` 전체가 그린인지 확인하라는 지침으로 마무리한다.

## 검증 레벨 선택

- **단위.** 순수 로직·서비스 단위. JUnit 5 + AssertJ + Mockito BDD. 협력 객체는 `given(...).willReturn(...)`. 외부 자원(DB·웹) 없이 실행된다.
- **슬라이스.** 웹 계층은 `@WebMvcTest` + `@MockitoBean`, 영속 계층은 `@DataJpaTest`. 도메인 전체를 띄우지 않고 해당 계층만 띄워 빠르게 검증한다.
- **통합.** `@SpringBootTest` + `@AutoConfigureMockMvc`(Boot 4는 MockMvc를 자동 주입하지 않으므로 명시 필요). DB 연동은 Testcontainers의 `@ServiceConnection`을 쓴다.

## 테스트 작성 원칙

- **독립과 순서 무관.** 테스트 간 상태를 공유하지 않는다. 이름·생성 시각이 다른 픽스처를 지향한다.
- **이름은 시나리오를 드러낸다.** `givenXxx_whenYyy_thenZzz` 또는 한글 시나리오 `사용자가_리뷰를_저장하면_목록에_보인다`.
- **검증은 AssertJ fluent.** `assertThat(result).isEqualTo(...)` 형태. 의미 있는 요소만 검증한다.
- **externally observable.** 전용 getter보다 외부 동작(응답 상태, 뷰 모델, 저장 결과)을 검증한다.
- **슬라이스 테스트와 트랜잭션.** `@DataJpaTest`는 기본 롤백이라 저장 확인 테스트는 그 안에서만. 직접 만든 `@Transactional` 통합 테스트와 혼동하지 않는다.
- **테스트가 느리면 함정이 아니다, 신호다.** 컨텍스트 캐시를 활용하고, 불필요한 풀 부팅을 피한다.

## 리뷰 기준

리뷰 요청은 정확성, 최신 스택 문법(spring-boot4), 계층 분리, 테스트 가능성, TDD 준수 여부로 지적한다.
"테스트가 먼저 명세인지", given/when/then이 시나리오를 하나만 검증하는지, Boot 4 스타터·어노테이션이 맞는지가 주요 관찰점이다.
예시 패턴과 코드 골격은 `references/test-patterns.md`에 있다.
